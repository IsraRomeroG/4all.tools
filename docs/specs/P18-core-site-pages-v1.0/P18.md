# P18 — Core Site Pages Publication

> **Phase ID:** `P18`  
> **Version:** 1.0.0  
> **Status:** Ready  
> **Baseline:** `72dc1194b97559b475c7f500e5d911d1d2e22898`  
> **Depends on:** P17 Complete  
> **Risk:** Medium technical / High editorial accuracy for legal copy

## 1. Purpose

Use the completed P17 site-page infrastructure to publish four core site-owned editorial documents:

```text
about
contact
terms
privacy
```

Each stable page identity MUST have one published translation in every supported locale:

```text
en
es
pt
fr
```

P18 also makes the pages discoverable through a global localized footer and extends the existing route, SEO, sitemap, build, and verification contracts.

The target flow remains:

```text
localized Markdown in sitePages
          ↓
PublishedContentIndexes.sitePages
          ↓
RouteRegistry
  area: site
  target.kind: site-page
          ↓
[root]/index.astro
          ↓
composeSitePageModel()
          ↓
SitePageTemplate.astro
          ↓
static HTML
```

No new page-delivery architecture is introduced.

## 4. SEO policy

P18 makes an explicit first-use decision for `seo.noindex`.

| Page ID | `noindex` | Sitemap |
|---|---:|---|
| `about` | `false` | included |
| `contact` | `false` | included |
| `terms` | `true` | excluded |
| `privacy` | `true` | excluded |

Rationale:

- About and Contact are useful trust/discovery pages and may be indexed.
- Terms and Privacy are utility/legal documents; P18 keeps them publicly accessible and internally linked while avoiding low-value index expansion.

All pages still require:

- self canonical;
- localized alternates derived from the route cluster;
- English `x-default` under the current SEO policy;
- correct `<html lang>`;
- localized title and meta description;
- no `/en/` output.

Do not hardcode canonical or alternate URLs in Markdown.

## 5. Content contract

The existing site-page schema remains sufficient:

```text
pageId
locale
routeSlug
status
title
seo
Markdown body
```

P18 MUST NOT add schema fields merely because Terms or Privacy commonly show dates.

If a legal document needs an effective/update date, render it as reviewed Markdown content in this phase. A structured field may be introduced later only when an actual consumer needs structured date semantics.

### About

The About page SHOULD explain:

- what 4all.tools is;
- its focus on useful web tools and supporting editorial content;
- multilingual availability;
- the product principle of describing each tool's execution/privacy behavior accurately.

Do not invent:

- a corporate entity;
- team size;
- offices;
- user counts;
- guarantees;
- broad claims that every current/future tool processes all data locally.

### Contact

P18 Contact is informational only.

It MUST:

- provide a real, site-owned contact channel approved for publication;
- explain appropriate reasons to contact the site;
- avoid publishing placeholder addresses such as `contact@example.com`;
- avoid introducing a form or backend.

The implementation owner MUST provide the real contact destination before the entry becomes `published`.

### Terms

Terms content MUST be reviewed before publication.

At minimum it should address, as applicable:

- scope/acceptance of site use;
- permitted use and prohibited misuse;
- responsibility for user-provided input;
- availability and change of services;
- intellectual-property/third-party considerations;
- disclaimers/limitations appropriate to the actual service;
- changes to the terms;
- contact channel;
- effective/update date as prose when desired.

Do not invent governing law, corporate identity, dispute venue, or jurisdiction-specific representations without an explicit owner/legal decision.

### Privacy

Privacy content MUST describe actual processing, not desired future behavior.

Before publication, verify at least:

- browser-local behavior of current interactive tools;
- cookies/local storage actually used by the site;
- analytics/telemetry actually present;
- third-party resources actually loaded;
- hosting/platform logs that may exist;
- information received when users contact the site;
- retention/deletion statements that can actually be honored.

The Privacy page MUST NOT claim “we collect no data” solely because the JSON Validator performs its core actions locally in the browser.

## 7. Public-route contract

The P18 baseline contains no production `site-page` RouteRecords.

P18 adds exactly:

```text
4 page identities × 4 locales = 16 new RouteRecords
```

The current 18-record public route contract therefore becomes:

```text
34 RouteRecords
```

assuming no unrelated route is added or removed during the phase.

The existing tool/blog routes MUST remain semantically unchanged.

The contract fixture must contain each new route as:

```ts
{
  area: 'site',
  locale,
  segments: [routeSlug],
  target: {
    kind: 'site-page',
    pageId,
  },
}
```

Use the actual deterministic `RouteRegistry` ordering. Do not introduce a second manually sorted route source in production.

## 8. Global footer navigation

P18 adds a global localized footer for:

```text
About
Contact
Privacy
Terms
```

Footer policy is navigation curation, not route ownership.

A recommended stable ordering is:

```text
about
contact
privacy
terms
```

The footer MAY define this ordered list of stable page IDs as navigation policy, but it MUST resolve the current locale's URL through `RouteRegistry`.

Forbidden:

```ts
href: '/about/'
href: '/es/acerca-de/'
```

as duplicated per-locale route catalogs inside the footer.

Expected conceptual flow:

```text
CORE_SITE_FOOTER_PAGE_IDS
        +
locale
        +
RouteRegistry.getCanonical(locale, { kind: 'site-page', pageId })
        +
localized footer labels
        ↓
SiteFooterModel
        ↓
SiteFooter.astro
```

`BaseLayout` already has a `site-footer` slot. P18 should use the existing slot rather than creating another layout boundary.

---

## 9. Footer model constraints

A footer link model SHOULD contain only consumer-facing data, for example:

```ts
interface SiteFooterLinkModel {
  readonly pageId: SitePageId;
  readonly label: string;
  readonly url: string;
}

interface SiteFooterModel {
  readonly ariaLabel: string;
  readonly links: readonly SiteFooterLinkModel[];
}
```

Exact file organization is implementation-defined, but the natural boundary is:

```text
src/navigation/site-footer/
```

The builder MUST:

- use stable `pageId` values;
- resolve canonical routes from `RouteRegistry`;
- derive relative URLs through the existing localized URL builder;
- reject malformed/non-internal URLs;
- preserve deterministic link order;
- avoid content fallback between locales.

Because P18 requires all four pages in all four locales, a missing required footer route is a build/test failure rather than a silent fallback to English.

## 10. Global messages

The current footer message group already contains Privacy and Terms labels. P18 SHOULD extend it with the missing navigation copy instead of creating a separate translation system.

Required semantic keys:

```text
footer.label
footer.about
footer.contact
footer.privacy
footer.terms
```

All four locales must satisfy `GlobalMessages`.

The footer label is for accessible navigation naming and must be localized.

## 11. Integration with page models/templates

The footer must be available on all normal public page families:

```text
home
tool
tool-category
blog-index
blog-category
article
site-page
```

Do not let `SiteFooter.astro` discover content or routes itself.

Two acceptable implementation shapes are:

1. add a shared footer model to the common page delivery model and compose it through the existing composers; or
2. introduce an equivalent shared page-shell composition that keeps route/content lookup outside Astro presentation components.

Whichever shape is chosen:

- `SiteFooter.astro` receives a prepared model;
- templates/layouts do not query Content Collections;
- templates/layouts do not build canonical route identities;
- no duplicated page-specific footer URL logic is introduced.

Do not broaden P18 into a general navigation/header redesign.

---

## 12. Out of scope

P18 does not include:

- contact form;
- backend/API/email sending;
- CAPTCHA;
- newsletter;
- user accounts;
- cookie-consent UI;
- analytics implementation;
- CMS;
- schema-selected layouts;
- nested site pages;
- legal version history;
- structured `effectiveDate` / `updatedAt` fields;
- jurisdiction-specific legal advice;
- redirects from unknown legacy URLs;
- a header/navigation redesign;
- additional site-page families.

## 14. Definition of Done

P18 is complete when:

- 16 production site-page Markdown entries exist;
- all 16 expected URLs are generated;
- `PUBLIC_ROUTE_INVENTORY` contains exactly the new site-page routes plus all prior routes;
- About and Contact are indexable;
- Terms and Privacy are `noindex` and excluded from sitemap output;
- each page has correct canonical, localized alternates and language-switcher behavior;
- all pages are linked from a localized global footer;
- footer URLs are derived from `RouteRegistry`, not duplicated;
- no contact form/backend is added;
- no site-page schema expansion is added without a real structured consumer;
- legal/privacy content has no placeholders or knowingly false data-processing claims;
- English remains unprefixed;
- current public tool/blog URLs are unchanged;
- durable architecture/project documentation is updated;
- `npm run verify` passes;
- GitHub Actions `Verify / verify` passes for the closing commit.
