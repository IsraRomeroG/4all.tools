# P19 — Global Site Header & Primary Navigation

> **Phase ID:** `P19`  
> **Version:** 1.1.0  
> **Status:** Ready  
> **Baseline:** `74c12ade66801e5a92de48a659460cab8ab9302c`  
> **Depends on:** P18 Complete  
> **Risk:** Low–Medium

## 1. Purpose

Create a reusable global site header for every normal public page in 4all.tools.

The current architecture already has:

```text
BaseLayout
├── slot="site-header"
├── <main>
└── slot="site-footer"
```

P18 filled the footer boundary. P19 fills the header boundary.

Today, templates place `LanguageSwitcher.astro` directly into `slot="site-header"`. P19 replaces that temporary arrangement with:

```text
page composer
     ↓
SiteHeaderModel
     ↓
SiteHeader.astro
     ↓
BaseLayout slot="site-header"
```

The existing language-switcher model becomes part of the header model rather than remaining top-level page presentation data.

---

## 2. Scope

P19 primary navigation contains only destinations that already exist and have stable URL semantics:

```text
Brand / Home
Blog
Language switcher
```

### Brand / Home

Visible brand:

```text
4all.tools
```

Localized hrefs:

```text
en → /
es → /es/
pt → /pt/
fr → /fr/
```

### Blog

Visible label comes from existing localized messages.

Localized hrefs:

```text
en → /blog/
es → /es/blog/
pt → /pt/blog/
fr → /fr/blog/
```

### Language switcher

Reuse the current language-switcher contracts and route-cluster behavior:

```text
current
available
unavailable
```

No locale fallback or route synthesis is added.

## 3. Explicit non-goals

P19 MUST NOT add primary navigation entries for:

```text
Tools
Categories
Search
About
Contact
Privacy
Terms
Pricing
Login
Register
Dashboard
```

Reasons:

- there is no public Tools index yet;
- there is no public Categories index yet;
- Search is not yet a finished global feature;
- About/Contact/Privacy/Terms already have an appropriate global home in the footer;
- authentication/product surfaces do not exist.

Do not expose navigation merely because a label already exists in the message catalog.

---

## 4. No hamburger in P19

P19 does not introduce a mobile hamburger/disclosure menu.

The current navigation density is too small to justify client-side menu state:

```text
brand + one primary destination + language switcher
```

The first header should remain fully usable without JavaScript.

Responsive behavior should be achieved through layout:

```text
flex
flex-wrap
responsive gaps
language area wrapping/full-width at narrow sizes when needed
```

A future navigation-density phase may introduce a mobile disclosure when the number of primary destinations justifies it.

The existing `accessibility.openMenu` and `accessibility.closeMenu` messages remain valid but unused by P19.

## 6. URL authority

Header links MUST use existing URL-building authorities.

### Home

Use:

```ts
buildLocalizedPath({
  locale,
  segments: [],
})
```

This already resolves:

```text
en → /
es → /es/
pt → /pt/
fr → /fr/
```

### Blog index

Use:

```ts
buildLocalizedPath({
  locale,
  segments: [BLOG_ROUTE_ROOT_SEGMENT],
})
```

where:

```ts
BLOG_ROUTE_ROOT_SEGMENT === 'blog'
```

Do not duplicate:

```ts
{
  en: '/blog/',
  es: '/es/blog/',
  ...
}
```

inside header code.

### Why RouteRegistry is not used here

Home and Blog index are fixed site surfaces and are not currently represented as production `RouteRecord`s in `PUBLIC_ROUTE_INVENTORY`.

P19 MUST NOT create fake/synthetic `RouteRecord`s only to make the header implementation symmetrical with the footer.

The correct authority distinction is:

```text
route-bearing content/tool entities
        → RouteRegistry

fixed Home / Blog-index surfaces
        → existing localized path builders
```

## 8. SiteHeader model

Recommended contracts:

```ts
export type SiteHeaderPageContext =
  | 'home'
  | 'blog-index'
  | 'blog-descendant'
  | 'other';

export interface SiteHeaderBrandModel {
  readonly label: string;
  readonly ariaLabel: string;
  readonly url: string;
  readonly active: boolean;
  readonly ariaCurrent?: 'page';
}

export interface SiteHeaderLinkModel {
  readonly id: 'blog';
  readonly label: string;
  readonly url: string;
  readonly active: boolean;
  readonly ariaCurrent?: 'page';
}

export interface SiteHeaderModel {
  readonly brand: SiteHeaderBrandModel;
  readonly primaryNavigationLabel: string;
  readonly primaryLinks: readonly SiteHeaderLinkModel[];
  readonly languageSwitcher: LanguageSwitcherModel;
}
```

Exact naming may vary slightly if it improves consistency with current project conventions, but the consumer-facing meaning must remain equivalent.

Do not expose routing/domain objects to `SiteHeader.astro` when strings/booleans are sufficient.

## 9. Active-section and current-page semantics

Visual section activity and exact-current-page semantics are different
contracts. Both must be determined by the page composer, not by comparing the
current pathname string.

Required mapping:

```text
home
  → pageContext = home
  → brand.active = true
  → brand.ariaCurrent = page

blog-index
  → pageContext = blog-index
  → Blog.active = true
  → Blog.ariaCurrent = page

blog-category
article
  → pageContext = blog-descendant
  → Blog.active = true
  → Blog.ariaCurrent is absent

tool
tool-category
site-page
  → pageContext = other
  → brand.active = false
  → Blog.active = false
  → both ariaCurrent values are absent
```

Expected UI semantics:

- on Home, the brand/home link carries `aria-current="page"`;
- on the Blog index, the Blog primary link carries `aria-current="page"`;
- on Blog Category and Article pages, Blog may remain visually active but MUST NOT carry `aria-current="page"` because its URL points to the Blog index rather than the displayed document;
- on Tool, Tool Category, and Site Page routes, neither Home nor Blog is active or current.

`active` may drive classes or a `data-active` marker. It MUST NOT be converted
mechanically into `aria-current`. The component emits `aria-current` only from
the explicit `ariaCurrent` field prepared by the builder.

Do not infer current state by:

```ts
Astro.url.pathname.startsWith(...)
```

inside the component.

## 10. SiteHeader builder

Recommended input:

```ts
export interface BuildSiteHeaderModelInput {
  readonly locale: Locale;
  readonly pageContext: SiteHeaderPageContext;
  readonly localizedRouteCluster: LocalizedRouteCluster;
  readonly messages: GlobalMessages;
}
```

The builder SHOULD:

1. build localized Home URL with `buildLocalizedPath`;
2. build localized Blog URL with `BLOG_ROUTE_ROOT_SEGMENT`;
3. use `messages.nav.home` for the accessible Home meaning;
4. use `messages.nav.blog` for the Blog label;
5. use a localized primary-navigation aria label;
6. call the existing `buildLanguageSwitcherModel()` with the current page's localized route cluster;
7. derive visual `active` state and exact `ariaCurrent` state from `pageContext` without allowing invalid combinations;
8. return immutable consumer-facing data where current project conventions require it.

This makes the language switcher a contained part of the global header:

```text
LocalizedRouteCluster
      ↓
buildLanguageSwitcherModel
      ↓
SiteHeaderModel.languageSwitcher
```

No second language-switcher algorithm is introduced.

## 12. LanguageSwitcher presentation refactor

The current `LanguageSwitcher.astro` owns a full-width visual bar:

```text
border
background
horizontal page padding
max-width container
```

After P19, `SiteHeader.astro` owns the global header shell.

Therefore `LanguageSwitcher.astro` SHOULD be reduced to a reusable embedded navigation component:

```text
<nav data-language-switcher ...>
  <ul>
    ...
  </ul>
</nav>
```

It must preserve:

- `aria-label`;
- current/available/unavailable states;
- `hreflang`;
- `lang`;
- `aria-current`;
- unavailable semantics;
- `data-language-switcher`;
- existing route correctness.

Do not duplicate LanguageSwitcher markup inside SiteHeader.

## 13. SiteHeader presentation

Create:

```text
src/components/navigation/SiteHeader.astro
```

It receives only:

```ts
model: SiteHeaderModel
```

It MUST NOT import:

```text
Content Collections
RouteRegistry
Astro.url for navigation decisions
taxonomy
page composers
SEO resolvers
```

It MAY import:

```text
LanguageSwitcher.astro
SiteHeaderModel type
```

Expected semantic shape:

```html
<header data-site-header>
  <div>
    <a data-site-brand>4all.tools</a>

    <nav aria-label="...">
      <a data-site-header-link="blog">Blog</a>
    </nav>

    <LanguageSwitcher />
  </div>
</header>
```

Exact wrappers are implementation-defined.

Every rendered document has exactly one global `<header data-site-header>`.
This does not prohibit legitimate editorial or section-level `<header>`
elements already used by templates and layouts.

## 14. Responsive visual contract

P19 is not a visual redesign phase, but the header must be usable from narrow mobile widths through desktop.

Required behavior:

- no horizontal page overflow;
- brand remains visible;
- Blog remains reachable;
- all supported language states remain reachable/visible;
- language labels may wrap;
- touch targets must remain usable;
- focus indicators remain visible;
- layout remains readable at narrow viewport widths.

Recommended design baseline:

```text
white background
slate border-bottom
max-width consistent with current templates/footer
compact vertical rhythm
brand visually stronger than navigation links
```

No sticky/fixed positioning is required.

No logo image is required.

## 15. Page-model migration

Target consumer-facing model state for models that extend the shared contract:

```ts
PageDocumentModel
    └── siteHeader: SiteHeaderModel
```

The current Blog models in `src/templates/models/blog.ts` do not extend
`PageDocumentModel`. P19 MUST therefore either:

1. add `siteHeader: SiteHeaderModel` explicitly to `BlogIndexPageModel`,
   `BlogCategoryPageModel`, and `ArticlePageModel`; or
2. deliberately refactor those models to extend the shared contract without
   weakening any existing required fields.

The minimal, preferred P19 change is the explicit property addition. Do not
assume that changing `PageDocumentModel` automatically migrates Blog models.

P19 SHOULD make `siteHeader` a required part of normal page delivery because every normal public page has enough data to build it.

The old top-level:

```ts
languageSwitcher: LanguageSwitcherModel
```

SHOULD be removed from consumer-facing page models once all templates render it through `SiteHeaderModel`.

Do not leave both indefinitely:

```text
page.languageSwitcher
page.siteHeader.languageSwitcher
```

That would duplicate presentation authority.

This is a hard internal migration; compatibility aliases are not required unless a real external consumer exists.

P19 also preserves the P17-C02 consumer boundary for site pages:

```text
composeSitePageModel local seoComposition.localizedRouteCluster
  → buildSiteHeaderModel input
  → NOT SitePageModel.localizedRouteCluster
```

`SitePageModel` must continue not to expose `localizedRouteCluster` as an own
consumer-facing property. The existing regression assertions for that absence
remain required.

## 16. Composer mapping

Each current composer produces its page-specific active section:

```text
composeHomePageModel
  → home

composeBlogIndexPageModel
  → blog-index

composeBlogCategoryPageModel
composeArticlePageModel
  → blog-descendant

composeToolPageModel
composeCategoryPageModel
composeSitePageModel
  → other
```

Each composer passes its already-computed `LocalizedRouteCluster` into the
header builder as an internal input. This does not authorize adding the cluster
to consumer models that intentionally omit it.

Do not recalculate SEO/localization clusters inside `SiteHeader.astro`.

Footer composition remains unchanged.

## 23. Definition of Done

P19 is complete when:

- `SiteHeaderModel` exists;
- `buildSiteHeaderModel()` exists;
- Home and Blog URLs are derived from existing localized routing builders;
- SiteHeader contains only Brand/Home + Blog + LanguageSwitcher;
- the existing LanguageSwitcher behavior is embedded, not reimplemented;
- `SiteHeader.astro` is presentation-only;
- every normal public template uses `SiteHeader` in `slot="site-header"`;
- consumer page models no longer expose duplicate top-level language-switcher presentation state;
- visual active states and exact-current-page semantics are distinct, semantic, and not pathname-derived;
- layout works without JS on narrow and wide viewports;
- no new public routes exist;
- `PUBLIC_ROUTE_INVENTORY` remains 34;
- canonical/SEO/sitemap output remains unchanged;
- generic static-output tests require exactly one global `data-site-header` on production pages while allowing editorial `<header>` elements;
- durable docs are updated;
- the complete v1.1 package is checked into `docs/specs/P19-global-site-header-v1.1/`;
- `npm run verify` passes;
- closing GitHub Actions `Verify / verify` passes.
