# P17 — Infraestructura de páginas estáticas editoriales

> **Phase ID:** `P17`
> **Version:** 1.0.0
> **Status:** Ready
> **Depends on:** P16 Complete
> **Risk:** Medium

## Propósito

Incorporar una única familia reutilizable de páginas editoriales estáticas y localizadas —por ejemplo contacto, privacidad o términos— sin crear una página Astro específica por traducción ni duplicar las autoridades actuales de contenido, routing o SEO.

El flujo objetivo es:

```text
Markdown localizado publicado
        ↓
índice de contenido exacto por pageId + locale
        ↓
RouteRecord static-page
        ↓
proyección del adaptador raíz existente
        ↓
composer + StaticPageTemplate
        ↓
HTML estático localizado
```

P17 entrega infraestructura. No publica todavía una página real ni una URL nueva.

## Estado de partida

El proyecto ya dispone de:

- `output: 'static'` y barra final obligatoria;
- inglés sin prefijo y `es`, `pt`, `fr` con prefijo;
- contenido localizado con publicación y consultas exactas;
- `RouteRegistry`, validación de colisiones y namespaces reservados;
- composición central de canonical, `hreflang`, `x-default` y `noindex`;
- selector de idioma basado en variantes del mismo destino estable;
- un adaptador dinámico raíz para rutas de un segmento.

La infraestructura todavía no dispone de:

- colección de páginas estáticas;
- identidad `static-page` dentro de `RouteTarget`;
- publicación de `RouteRecord`s en el área `static`;
- proyección estática y dispatch de esa familia;
- modelo, composer y template editoriales estáticos.

## Decisiones de alcance

### Autoridades

- Una traducción publicada de la colección `staticPages` es la autoridad de disponibilidad, slug localizado y contenido editorial.
- `pageId` es estable y compartido por las traducciones de la misma página.
- `routeSlug` es localizado y contiene exactamente un segmento.
- `RouteRegistry` sigue siendo la autoridad de la URL pública, canonical y variantes localizadas.
- El frontmatter no contiene `canonicalUrl`, alternates ni URLs absolutas.

### Contrato editorial mínimo

Cada entrada necesita solamente:

```text
pageId
locale
routeSlug
status
title
seo
Markdown body
```

No se añaden campos opcionales anticipatorios como resumen, fechas legales, autor, plantilla, jerarquía, tipo de página o configuración de formulario.

### Routing

- Las páginas de P17 son planas y viven en la raíz de cada locale.
- Ejemplo futuro, no publicado por esta fase:

  ```text
  en + contact  → /contact/
  es + contacto → /es/contacto/
  pt + contato  → /pt/contato/
  fr + contact  → /fr/contact/
  ```

- Inglés continúa sin `/en/`.
- Una traducción ausente o no publicada no genera ruta, alternate ni enlace disponible en el selector de idioma.
- No existe fallback de contenido entre locales.
- La implementación debe reutilizar o generalizar el adaptador raíz de un segmento; no debe introducir otro patrón dinámico competidor.
- P17 no renombra los adaptadores `[category]` existentes: cambiar su nombre interno no aporta comportamiento y ampliaría innecesariamente el cambio.

### Entrega

- Un `StaticPageModel` resuelto contiene ruta, SEO, selector de idioma, título y Markdown renderizado. El cluster localizado se usa durante la composición, pero no se expone en el modelo si ningún consumidor lo necesita.
- Un `StaticPageTemplate.astro` usa `BaseLayout`, `SeoHead` y `LanguageSwitcher`.
- El template no consulta contenido, no conoce el registro de rutas y no construye URLs.
- El adaptador Astro recibe `routeTarget` mediante `getStaticPaths()` y no infiere identidad desde el slug.

## Fuera de alcance

- contenido productivo de contacto, privacidad, términos o cualquier otra página;
- formularios, envío de correo, CAPTCHA, API o servicio externo;
- footer, header o navegación global nueva;
- breadcrumbs para páginas de un solo nivel;
- rutas anidadas o jerarquía de páginas;
- aliases, múltiples URLs por locale o redirect registry;
- reglas Apache `.htaccess`;
- CMS, preview editorial o traducción automática;
- fechas de vigencia, historial de versiones o metadatos legales;
- componentes o layouts seleccionables desde frontmatter;
- JSON-LD u otros tipos SEO nuevos;
- dependencias nuevas.

Cada capacidad anterior requiere un consumidor y requisitos propios antes de incorporarse.

## Grafo de tareas

```text
P17-T01 → P17-T02 → P17-T03 → P17-T04
```

- `P17-T01`: contrato, colección e índices de contenido.
- `P17-T02`: publicación localizada en routing y proyección estática.
- `P17-T03`: modelo, composer, template y adaptadores.
- `P17-T04`: verificación y documentación de cierre.

## Política de rutas canónicas

P17 no modifica ni retira ninguna URL pública existente y no publica URLs nuevas, por lo que no existe un mapa `old → new` ni se requieren redirecciones.

La primera tarea futura que publique una página real debe congelar su matriz `pageId + locale + routeSlug`, actualizar el inventario público y decidir por separado cualquier migración de URLs preexistentes. No se conservarán páginas Astro duplicadas como rutas legacy.

## Definition of Done

- existe una colección mínima `staticPages` con consultas exactas y sin fallback;
- cada traducción publicada produce como máximo un `RouteRecord` `static-page`;
- los slugs localizados planos usan el builder de URLs existente;
- colisiones y namespaces reservados se validan por las reglas comunes;
- el adaptador raíz existente puede proyectar categorías raíz y páginas estáticas sin solapamiento;
- un modelo y template compartidos renderizan contenido, SEO y selector de idioma;
- no se publica contenido placeholder ni una URL de demostración;
- no se añade una segunda autoridad de rutas, un registro paralelo o una abstracción de jerarquía;
- las pruebas protegen comportamiento durable, no nombres internos de helpers;
- la documentación vigente describe la nueva familia;
- `npm run verify` finaliza correctamente.
