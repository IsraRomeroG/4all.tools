# P17-C02 — Site Page Semantic Alignment

> **Correction ID:** `P17-C02`  
> **Version:** 1.0.0  
> **Status:** Complete
> **Baseline:** `8895918056b1e5a32a2ae47664d462c27cc36bad`  
> **Depends on:** P17 v1.1 correction closure  
> **Risk:** Medium
> **Amended by:** P17-C02
> **Current terminology:** `site-page`

## 1. Purpose

Rename and align the P17 editorial-page infrastructure before the first real editorial root page is published.

The term `static-page` is replaced by `site-page` because `static` describes the deployment/rendering mode of most of the Astro application, while `site-page` describes the semantic role of this family: independent site-owned editorial documents such as Contact, Privacy, Terms, or About.

The correction also generalizes the root route adapter. After P17, the existing `[category]` root adapter can dispatch both root tool categories and editorial pages, so `category` is no longer an accurate name for its routing responsibility.

## 2. Target architecture

```text
localized Markdown in sitePages
          ↓
PublishedContentIndexes.sitePages
          ↓
RouteRecord
  area: site
  target.kind: site-page
          ↓
RouteRegistry
          ↓
root static-path projection
          ↓
[root]/index.astro
          ↓
composeRootAdapterPage()
          ↓
SitePageModel
          ↓
SitePageTemplate.astro
          ↓
static HTML
```

Root tool categories continue through the same root adapter family:

```text
RouteTarget
   ├── tool-category → CategoryTemplate
   └── site-page     → SitePageTemplate
```

## 3. Semantic rename contract

| Current P17 name | Target name |

| `StaticPageId` | `SitePageId` |
| `staticPages` | `sitePages` |
| `src/content/static-pages/` | `src/content/site-pages/` |
| `staticPageContentSchema` | `sitePageContentSchema` |
| `StaticPageContentData` | `SitePageContentData` |
| `StaticPageContentEntry` | `SitePageContentEntry` |

## 4. Authority invariants

The correction MUST preserve the single-authority model:

```text
sitePages Markdown
  → page identity + localized slug + publication + editorial body + SEO input

RouteRegistry
  → public route + canonical route + localized target variants

Composer
  → resolved delivery model

Template
  → presentation only
```

P17-C02 MUST NOT introduce:

- `SitePageRegistry`;
- a route catalog parallel to `RouteRegistry`;
- a content repository abstraction;
- a site-page-specific URL registry;
- canonical URLs in frontmatter;
- a second root dynamic Astro route family;
- compatibility aliases for every old `StaticPage*` symbol;
- a second `staticPages` collection kept beside `sitePages`.

## 5. Public-route freeze

No production site-page content exists at the baseline. Therefore:

- `PUBLIC_ROUTE_INVENTORY` MUST remain semantically unchanged;
- no `target.kind = 'site-page'` record may appear in the production inventory;
- no new output such as `/contact/`, `/privacy/`, `/terms/`, or `/about/` may appear;
- existing tools, category, home, and blog URLs MUST remain unchanged;
- English remains unprefixed;
- `/en/` MUST not appear.

A parity failure is a stop condition, not an expected update for this correction.

## 6. Site-page admission rule

A `site-page` is an independent, site-owned, non-taxonomic editorial document that:

1. has one stable `pageId` shared by its translations;
2. has at most one published canonical route per locale;
3. lives at one root segment relative to its locale;
4. is primarily Markdown editorial content;
5. does not represent a tool, tool category, blog category, article, or other existing domain entity;
6. does not require a dedicated feature architecture for its primary behavior.

Typical fits:

```text
Contact information  → site-page
Privacy policy       → site-page
Terms of service     → site-page
About                → usually site-page
```

Non-fits:

```text
Developer category   → tool-category
JSON Validator       → tool
Blog article         → article
Blog category        → blog-category
Interactive product  → dedicated feature/family
```

A page such as Pricing MUST be classified when its actual requirements exist. Do not force future product surfaces into `sitePages` merely because they happen to live at the root.

## 7. `content/site` vs `content/site-pages`

The durable boundary is:

```text
src/content/site/
  → code-owned singleton/shared site copy or fixed surface content
  → does not self-publish RouteRecords
  → examples: current blog-index copy

src/content/site-pages/
  → localized publishable Markdown documents
  → each document has SitePageId + locale + routeSlug
  → published entries generate RouteRecords
```

The two folders MUST NOT become alternative ways to publish the same kind of page.

## 9. Definition of Done

P17-C02 is complete when:

- active production code uses `site-page` terminology consistently;
- `RouteTarget` uses `kind: 'site-page'` and `SitePageId`;
- route area is `site` rather than `static`;
- Astro Content uses collection `sitePages` from `src/content/site-pages/`;
- the root adapter uses a neutral root-segment name rather than `category`;
- site-page delivery uses `SitePageModel`, `composeSitePageModel`, and `SitePageTemplate`;
- admission and content-boundary rules are documented;
- no dual old/new compatibility layer remains without a demonstrated consumer;
- no production site-page content is added;
- the public route contract remains identical;
- `npm run verify` passes.
